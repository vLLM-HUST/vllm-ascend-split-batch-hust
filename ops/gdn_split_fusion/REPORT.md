# 算子验收报告: GDN Projection Unpack / Mixed-QKV Rearrange Fusion

## 1. 评测环境与形状事实

- **硬件拓扑**: Atlas 800T A2 (2×910B2, TP=2)
- **环境版本**: CANN 9.1.0 / vllm `0.28.1.post1.dev143+gf18cf803c` / vllm-ascend `0.25.1rc2.dev125+hust`
- **模型**: Qwen3.5-35B-A3B (bf16)，30 层 GDN + 10 层 full attention，`gqa_interleaved_layout=False`
- **形状**: ① `qkvz` 每行 `2048 + 1024 = 3072`，`ba` 宽 `256`；② `mixed_qkv` 每行 `1024 + 1024 + 2048 = 4096`，`head_k_dim = head_v_dim = 128`
- **图模式**: `cudagraph_mode=FULL`，capture `[1,2,4,8,16,32]`，APC off
- **开关**: `VLLM_HUST_GDN_UNPACK_FUSED=1`，默认 `0`

## 2. 单算子微基准

NPU graph 内打包（decode 50×、prefill 5×）后摊 replay，单卡 910B2，单位 µs/层·step：

**组件 ①（投影解包）**

| M | 原生 | 融合 | 省 | 省% | 逐位一致 |
|---|---|---|---|---|---|
| 1 | 0.37 | 1.85 | −1.48 | 走原生 | ✅ |
| 8 | 5.06 | **1.56** | 3.50 | 69.2% | ✅ |
| 32 | 6.19 | **3.43** | 2.76 | 44.6% | ✅ |
| 266 | 9.19 | **6.74** | 2.45 | 26.7% | ✅ |
| 1867 | 14.53 | **9.36** | 5.17 | 35.6% | ✅ |

**组件 ②（混合 qkv 重排）**

| M | 原生 | 融合 | 省 | 省% | 逐位一致 |
|---|---|---|---|---|---|
| 1 | 0.34 | 1.77 | −1.43 | 走原生 | ✅ |
| 8 | 5.13 | **1.59** | 3.53 | 68.8% | ✅ |
| 32 | 6.18 | **3.17** | 3.02 | 48.9% | ✅ |
| 266 | 10.10 | **7.55** | 2.55 | 25.2% | ✅ |
| 1867 | 22.45 | **11.11** | 11.34 | 50.5% | ✅ |

**投影（M=8、30 层、64 step）**：`7.03 × 1920 = 13.5 ms`，约为 decode 非通信时间（515.2 ms）的 2.6%。

⚠ 这个投影已被 §5 的线上归因修正为 **0.39%**：线上并发是 32 而不是 8，`ConcatD` 与融合 kernel 两侧成本都被放大，净差被稀释。以 §5 为准。

两点值得记录：

- **prefill 也正收益**。上一版用 `grid = rows`（一行一 program），prefill 上碎得厉害，只能超过 32 行就回退；本版换成核数分块 + UB 分批后，M=266 省 5.0 µs、M=1867 省 16.5 µs。
- **M=1 是负收益**，见 §4。

## 3. 数值护栏

- **已做（算子级）**：5 档 M（1/8/32/266/1867）逐位对拍全部相等，覆盖 decode 与 prefill。
- **未做（端到端）**：8 条固定 prompt 的贪心对拍还没跑；需要两腿起服，尚未执行。

口径：算子级逐位等价成立；端到端未验，在此之前不得宣称"模型输出无差异"。

## 4. 已知问题：M=1 的 op 固定开销

M=1 时 op 内部回退到原生链，但调用 custom op 本身有约 **1.4 µs** 固定开销：

```
① 0.37 → 1.85 µs（+1.48）
② 0.34 → 1.77 µs（+1.43）
30 层合计 ≈ 84 µs/step
```

相对 66 ms 的每 token 耗时约 **0.13%**。当前接受，原因是形状判断必须留在 op 内——`forward` 在 dynamo 追踪范围内，Python 分支会被首个形状常量折叠。

若后续确认 vLLM 对 GDN 的 `forward` 会按形状重新追踪，可把判断移到 Python 层，消掉这部分开销。

## 5. 图内归因（已完成）

采集口径：32 请求 × 512 输出、并发 32、TP2 FULL graph，rank0 非通信算子汇总（`op_statistic`），覆盖整个 bench 窗口。

| 算子 | 关闭腿 | 开启腿 | 变化 |
|---|---|---|---|
| `Slice` | 117550 次 / 367.9 ms | 25557 次 / 74.7 ms | **−293.1 ms** |
| `ConcatD` | 15420 次 / 265.7 ms | 30 次 / 0.5 ms | **−265.2 ms** |
| `_unpack_kernel` | — | 15324 次 / 106.1 ms | +106.1 ms |
| `_rearrange_kernel` | — | 15324 次 / 101.9 ms | +101.9 ms |
| **目标组合计** | **633.5 ms** | **283.3 ms** | **−350.2 ms（−2.41%）** |
| 全部算子合计 | 14518.0 ms | 14198.3 ms | −319.7 ms（−2.20%） |

- **机制成立**：两个 kernel 各出现 15324 次 = 30 层 × 511 step，与预期（15330）吻合。
- **替换范围比预想的大**：`ConcatD` 15420 → 30 次，同时 `Slice` 从 117550 塌到 25557。被吃掉的 Slice 包括 `[32,6144]→[32,4096]`（`mixed_qkvz` 切 qkv）、`[32,32]→[32,16]`（`split_ba` 的 chunk，30540 次）、`[32,4096]→[32,1024]`（q/k/v 切分，30540 次）。
- **净可归因：−350.2 ms，占全部算子累计时间的 2.41%。**
- 全部算子的 −2.20% 比 2.41% 小，是因为其他算子同期反向漂移了约 30 ms。

> ⚠ **口径修正**：早先版本只统计了 `ConcatD`（−265.2 + 208.0 = −57.2 ms，0.39%），漏掉了 `Slice` 的 −293.1 ms。真实收益是 2.41%，不是 0.39%。

### 与微基准预测的偏差

微基准预测 2.6%，线上归因 2.41%，量级对上了。

但**构成不同**：微基准只覆盖 `split + 3×reshape + cat` 这一段；线上实际省下的还包括 q/k/v 切分和 `split_ba` 的 chunk——这两项在微基准里根本没有对应项，是上线后才暴露的额外收益。

单次成本对照：

| | 微基准 M=8 | 线上并发 32 |
|---|---|---|
| 原生 `ConcatD` | 6.18 µs | 17.2 µs |
| 融合 kernel 合计 | 3.17 µs | 13.6 µs |

两侧都放大了 2–4 倍，比例上互相抵消，所以总占比反而接近。

教训：微基准能预测量级，预测不了构成。

## 6. 服务端

两个负载各测了一遍，都用 ABBA 平衡设计，单腿 128 请求、并发 32、输出 256 token。

### 512 输入（66k KV token）：8 腿

| 块 | A（关闭） | B（开启） | tok/s | TPOT |
|---|---|---|---|---|
| 1 | 753.12 | 756.40 | +0.44% | −1.34% |
| 2 | 761.19 | 764.87 | +0.48% | −3.85% |
| 合并 | 757.15 | 760.63 | **+0.46%** | **−2.60%** |

两块方向一致为正，但幅度小于 A 腿自身的极差（4.18%）。

### 2048 输入（263k KV token）：12 腿

| 块 | A（关闭） | B（开启） | tok/s | TPOT |
|---|---|---|---|---|
| 1 | 450.15 | 416.37 | −7.50% | +4.03% |
| 2 | 452.89 | 446.89 | −1.32% | +0.58% |
| 3 | 441.71 | 438.90 | −0.64% | +0.76% |
| 合并 | 448.25 | 434.05 | −3.17% | +1.78% |

三块方向一致为负，但块 1 里有一条 B 腿（391.55）明显离群，比同配置其他腿低 11%。剔除后为 **−1.27%**，仍小于 A 腿极差（4.29%）。

### 判定

两个负载的差异都落在各自的腿间极差之内，**既不能主张收益，也不能主张损失**。

但有一件事必须记下来：

```
512  场景：算子省 2.41%   服务 +0.46%
2048 场景：算子省 5.05%   服务 −1.27%
```

**算子省得更多的场景，服务层反而略差。** 这不是"收益被摊薄"——摊薄应该是同向、幅度变小；这里是符号相反。

### 根因

`op_statistic` 把这段 bench 的算子耗时累加成 **14518 ms**，而这段 bench 的实际 wall time 要短得多。也就是说这些 kernel 并不是首尾相接地执行，中间存在大量空隙（等通信、等其他 stream）。

减少 350 ms 的 kernel 时间，只是让这些空隙变大，wall time 不变。

这也解释了为什么 2048 场景更糟：那个负载下 TP 通信量更大、空隙更多，去掉 kernel 后能"填进去"的工作更少，反而可能损失了原本靠这些 kernel 遮盖的等待窗口。

**注意**：TP 的 AllReduce 走 HCCL、在独立 stream 上，不进入 `op_statistic`（该表中通信类算子仅占 0.2%）。所以"通信占比多少"这个问题用现有工具回答不了，根因判断是从"算子累计 14518 ms 远大于 wall time"这个结构性事实推出的，不是直接测到的。

## 7. 结论

| 判据 | 结果 |
|---|---|
| 单算子微基准 | ✅ decode 省 7.03 µs/层·step，prefill 也正收益 |
| 算子级逐位一致 | ✅ 5 档 M 全部相等 |
| 端到端数值 | ✅ 8/8 逐条一致 |
| 图内归因（512） | ✅ `Slice` 117550→25557、`ConcatD` 15420→30，目标组 **−350.2 ms（2.41%）** |
| 图内归因（2048） | ✅ 目标组 **−3397 ms（5.05%）** |
| 服务端（512） | ⚠️ +0.46%（8 腿，两块同向为正，幅度小于 4.18% 腿间极差） |
| 服务端（2048） | ⚠️ −1.27%（12 腿，三块同向为负，幅度小于 4.29% 腿间极差） |

**交付决策：保持默认关闭（`default_off_serving_no_gain`）。**

理由不是「没测出来」，而是测出来之后发现**算子级收益与 wall time 脱节，且符号可能相反**：

```
512   算子 +2.41%   服务 +0.46%
2048  算子 +5.05%   服务 −1.27%
```

根因见 §6 末段：算子累计时间远大于 wall time，说明 kernel 之间有大量空隙，减少 kernel 时间只是把空隙撑大。

### 如果还要继续推

按 ROI 排序：

| 方向 | 可行性 | 预期 | 成本 |
|---|---|---|---|
| 消掉 custom op 的 1.4 µs dispatch | ❌ **已排除**。vLLM 用 dynamic shape 编译（日志只有一条 `compile range (1, 2048)`），Python 层形状判断会导致反复重编译或 graph break | — | — |
| 把 `l2norm_fwd` 融进 rearrange kernel | 技术可行，数值风险高 | 近翻倍（+6 µs） | 2–3 天 |
| 让 MatMul 直接输出到目标布局 | 要改算子 epilogue | 省 1.56 µs | 高 |
| prefill 大 M 调优 | 可行 | 2048 场景还有空间 | 1–2 天 |

**但以上都不会改变服务层结论**——除非先解决「为什么减少 kernel 时间不缩短 wall time」。要回答那个问题，需要 timeline 级的分析（按 stream 看空隙），`op_statistic` 看不到（通信走 HCCL、不在这张表里）。

### 一个更值得做的判断

这个算子的探索价值已经兑现：它证明了**在这套系统上，从「拷贝/小算子」出发的优化，收益会被 wall time 的结构锁死**。同样的现象在 MoE 门控乘融合上复现过（算子省 0.26%，服务层不可判定）。

真要把服务侧性能做上去，靶子应该换成 `GroupedMatmul`（占 28–45%）和 `MatMulV2`（占 13.6%，每层每步 9 次、单次 14.4 µs）。

## 8. 与上一版实现的差异

| 维度 | 上一版（跨仓库） | 本版（单仓库） |
|---|---|---|
| 仓库 | `vllm-ascend-hust` + `vllm-hust` | 仅 `vllm-ascend-hust` |
| 组件 ② 接入 | 改 vllm core 的 `rearrange_mixed_qkv` 本体 | 子类覆盖 + 改本仓库 3 处调用 |
| 网格 | `grid = (rows,)` | `grid = min(vector_core, rows)` + UB 分批 |
| prefill | 超过 32 行回退 | 全形状融合 |
| 开关 | 两个独立开关 | 一个开关 |
| op 注册 | `direct_register_custom_op` | `torch.library.custom_op` + `register_fake` |

上一版的宿主分支（`work/gdn-split-fusion`、`work/gdn-rearrange-fusion`）保留在仓库里作为历史，未合入基线。
