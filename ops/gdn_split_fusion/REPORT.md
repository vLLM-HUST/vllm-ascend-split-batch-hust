# 算子验收报告: GDN Projection Unpack / Mixed-QKV Rearrange Fusion

## 1. 评测环境与形状事实

- **硬件拓扑**: Atlas 800T A2 (2×910B2, TP=2)
- **环境版本**: CANN 9.1.0 / vllm `0.28.1.post1.dev143+gf18cf803c` / vllm-ascend `0.25.1rc2.dev125+hust`
- **模型**: Qwen3.5-35B-A3B (bf16)，30 层 GDN + 10 层 full attention，`gqa_interleaved_layout=False`
- **形状**: ① `qkvz` 每行 `2048 + 1024 = 3072`，`ba` 宽 `256`；② `mixed_qkv` 每行 `1024 + 1024 + 2048 = 4096`，`head_k_dim = head_v_dim = 128`
- **图模式**: `cudagraph_mode=FULL`，capture `[1,2,4,8,16,32]`，APC off
- **开关**: `VLLM_HUST_GDN_UNPACK_FUSED=1`，默认 `0`

## 2. 单算子微基准

NPU graph 内打包（decode 50×、prefill 5×）后摊 replay，单卡 910B2，单位 µs/层·step：

**组件 ①（投影解包）**

| M | 原生 | 融合 | 省 | 省% | 逐位一致 |
|---|---|---|---|---|---|
| 1 | 0.37 | 1.85 | −1.48 | 走原生 | ✅ |
| 8 | 5.06 | **1.56** | 3.50 | 69.2% | ✅ |
| 32 | 6.19 | **3.43** | 2.76 | 44.6% | ✅ |
| 266 | 9.19 | **6.74** | 2.45 | 26.7% | ✅ |
| 1867 | 14.53 | **9.36** | 5.17 | 35.6% | ✅ |

**组件 ②（混合 qkv 重排）**

| M | 原生 | 融合 | 省 | 省% | 逐位一致 |
|---|---|---|---|---|---|
| 1 | 0.34 | 1.77 | −1.43 | 走原生 | ✅ |
| 8 | 5.13 | **1.59** | 3.53 | 68.8% | ✅ |
| 32 | 6.18 | **3.17** | 3.02 | 48.9% | ✅ |
| 266 | 10.10 | **7.55** | 2.55 | 25.2% | ✅ |
| 1867 | 22.45 | **11.11** | 11.34 | 50.5% | ✅ |

**投影（M=8、30 层、64 step）**：`7.03 × 1920 = 13.5 ms`，约为 decode 非通信时间（515.2 ms）的 2.6%。

⚠ 这个投影已被 §5 的线上归因修正为 **0.39%**：线上并发是 32 而不是 8，`ConcatD` 与融合 kernel 两侧成本都被放大，净差被稀释。以 §5 为准。

两点值得记录：

- **prefill 也正收益**。上一版用 `grid = rows`（一行一 program），prefill 上碎得厉害，只能超过 32 行就回退；本版换成核数分块 + UB 分批后，M=266 省 5.0 µs、M=1867 省 16.5 µs。
- **M=1 是负收益**，见 §4。

## 3. 数值护栏

- **已做（算子级）**：5 档 M（1/8/32/266/1867）逐位对拍全部相等，覆盖 decode 与 prefill。
- **未做（端到端）**：8 条固定 prompt 的贪心对拍还没跑；需要两腿起服，尚未执行。

口径：算子级逐位等价成立；端到端未验，在此之前不得宣称"模型输出无差异"。

## 4. 已知问题：M=1 的 op 固定开销

M=1 时 op 内部回退到原生链，但调用 custom op 本身有约 **1.4 µs** 固定开销：

```
① 0.37 → 1.85 µs（+1.48）
② 0.34 → 1.77 µs（+1.43）
30 层合计 ≈ 84 µs/step
```

相对 66 ms 的每 token 耗时约 **0.13%**。当前接受，原因是形状判断必须留在 op 内——`forward` 在 dynamo 追踪范围内，Python 分支会被首个形状常量折叠。

若后续确认 vLLM 对 GDN 的 `forward` 会按形状重新追踪，可把判断移到 Python 层，消掉这部分开销。

## 5. 图内归因（已完成）

采集口径：32 请求 × 512 输出、并发 32、TP2 FULL graph，rank0 非通信算子汇总（`op_statistic`），覆盖整个 bench 窗口。

| 算子 | 关闭腿 | 开启腿 | 变化 |
|---|---|---|---|
| `ConcatD` | 15420 次 / 265.7 ms | 30 次 / 0.5 ms | **−265.2 ms** |
| `_unpack_kernel` | — | 15324 次 / 106.1 ms | +106.1 ms |
| `_rearrange_kernel` | — | 15324 次 / 101.9 ms | +101.9 ms |
| 全部算子合计 | 14518.0 ms | 14198.3 ms | −319.7 ms（−2.20%） |

- **机制成立**：两个 kernel 各出现 15324 次 = 30 层 × 511 step，与预期完全吻合（`call_count_expected` 15330）。
- **替换对象确认**：`ConcatD` 从 15420 次塌到 30 次（只剩 30 次是别处的），说明组件 ② 确实吃掉了原来的 `cat`。
- **净可归因**：`−265.2 + 208.0 = −57.2 ms`，占全部算子累计时间的 **−0.39%**。
- 全部算子 −2.20% 里还混着窗口漂移（`Transpose` 也降了 34.2 ms），不能全算作本项收益。

### 与微基准预测的偏差

微基准预测 2.6%，线上归因只有 0.39%，差 6 倍。原因有两个：

1. **batch 不匹配**。微基准用 M=8，线上并发 32，单次成本放大了：`ConcatD` 线上 17.2 µs/次，而微基准 M=32 的 stock 只有 6.18 µs。
2. **融合 kernel 同步放大**。两个 kernel 线上合计 13.6 µs/次，微基准 M=32 只有 3.17 µs。

净差因此从微基准的 3.01 µs 变成线上的 3.7 µs——**方向对，但被两侧放大稀释**：省下的是"17.2 − 13.6"，而不是"6.18 − 3.17"占原生链的比例。

教训：微基准的形状必须取线上真实并发。

## 6. 服务端

**未做。** 按修正后的 0.39% 口径，信号远小于同 cohort 2.04% 的腿间极差，8 腿 ABBA 在统计上无法分辨，不打算跑。

profiler 开启时两次采样的吞吐分别是 894.06 和 780.81 tok/s、TPOT 32.75 和 32.36 ms，波动本身就有 12%，进一步说明这个量级测不出。

## 7. 结论与待办

| 判据 | 结果 |
|---|---|
| 微基准收益 | ✅ decode 省 7.03 µs/层·step，prefill 也正收益 |
| 算子级逐位一致 | ✅ 5 档 M 全部相等 |
| 端到端数值 | ✅ 8/8 逐条一致 |
| 图内归因 | ✅ 两 kernel 各 15324 次，`ConcatD` 15420 → 30，净 −57.2 ms |
| 服务端 | ⏸ 不跑：0.39% 小于 2.04% 腿间极差 |

交付决策：**保持默认关闭**。在端到端与图内归因补齐前，只能作为「微基准通过、待验证」归档。

待办：

1. 决定 M=1 的 op 开销是否可接受（约 0.13% TPOT），或改成 Python 层判断。
2. 补齐 in_proj 合并路径（W3F2 开启时组件 ① 目前不生效）。
3. 若要提升收益量级，应针对线上真实并发（32）重新设计——`ConcatD` 单次 17.2 µs 是主要对手，而不是微基准里的 6.18 µs。

## 8. 与上一版实现的差异

| 维度 | 上一版（跨仓库） | 本版（单仓库） |
|---|---|---|
| 仓库 | `vllm-ascend-hust` + `vllm-hust` | 仅 `vllm-ascend-hust` |
| 组件 ② 接入 | 改 vllm core 的 `rearrange_mixed_qkv` 本体 | 子类覆盖 + 改本仓库 3 处调用 |
| 网格 | `grid = (rows,)` | `grid = min(vector_core, rows)` + UB 分批 |
| prefill | 超过 32 行回退 | 全形状融合 |
| 开关 | 两个独立开关 | 一个开关 |
| op 注册 | `direct_register_custom_op` | `torch.library.custom_op` + `register_fake` |

上一版的宿主分支（`work/gdn-split-fusion`、`work/gdn-rearrange-fusion`）保留在仓库里作为历史，未合入基线。
