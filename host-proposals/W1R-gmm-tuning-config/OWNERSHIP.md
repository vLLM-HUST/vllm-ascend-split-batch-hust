# W1R: GMM 调优参数与专家频次转储方案说明

## 1. 方案简介

本方案是一份**默认关闭的宿主代码修改提案**，目标是修改宿主文件 `vllm_ascend/ops/fused_moe/routed_experts.py` 中的两处 Grouped MatMul（GMM）调用，提供以下两个功能：

| 环境变量 | 作用 | 未设置时的默认行为 |
|---|---|---|
| `VLLM_HUST_GMM_TUNING_CONFIG` | 接收单值正整数参数（白名单：`1, 2, 8, 32`），传递给底层的 `apply_gmm1` 和 `apply_gmm2`。 | 保持原生逻辑，不传该参数。 |
| `VLLM_HUST_GMM_COUNTS_DUMP=<path>` | 采样记录 MoE 各专家的 Token 分配数量及输入张量形状，保存到指定文件。 | 不记录，不创建文件。 |

- **纯诊断性质**：该转储仅用于分析模型路由分布，不会改变任何数学计算结果。

## 2. 为什么需要修改宿主源码

1. **宿主未公开配置参数**：当前 vLLM-Ascend 官方接口没有暴露 `tuning_config` 调优参数；
2. **调用点在私有方法内部**：两处 GMM 调用点位于 `AscendUnquantizedFusedMoEMethod` 类内部私有方法中，外部插件无法以无侵入的方式直接拦截或修改参数；
3. **避免全局 Monkeypatch**：如果在全局打补丁拦截 `torch_npu.npu_grouped_matmul`，会波及模型内所有非 MoE 的矩阵乘法，风险过大。

## 3. 当前状态与阻塞原因（为什么被冻结）

- **当前状态**：**已冻结（Blocked），不进行实验，也不在生产环境中应用**。
- **核心阻塞原因**：
  - 在生产环境开启完整计算图（CUDA Graph / ACL Graph）的 Decode 模式下，整张图被捕获到底层硬件循环执行，执行期间完全不经过 Python 解释器。
  - 因此，我们在 Python 层添加的采样 Hook 无法在 Decode 执行时被触发，**无法统计到真实的每步专家调用频次**。
  - 虽然在非图模式（Eager / NONE 模式）下可以统计到数据，但非图模式不能代表图模式下的性能表现，不能用于正式评测。
- **处置结论**：
  - 本提案仅保留作为技术分析原件；
  - 容器运行树中已彻底移除该补丁，不进行任何动态挂载或性能评测。
